# Pull request

## Summary

Implements #2: a deterministic, seeded generator for a small longitudinal synthetic dataset, built against the draft v0.1.0 data contract proposed in #1. Field choices will follow whatever the #1 RFC settles on.

Closes #2. Refs #1.

What is included:

- **Draft v0.1.0 data contract** (`src/datalife_analytics/contracts/v0_1_0/data_dictionary.json`): three long-format tables (`subjects`, `encounters`, `observations`) with types, allowed values, plausible ranges, missingness semantics, temporal rules, forbidden identifier patterns and a semver versioning policy.
- **Generator** (`generator.py`): per-subject `SeedSequence` streams, so subject *i* is identical whatever the cohort size. Hand-set generic distributions, not fitted to any real data.
- **Validator** (`contract.py`): schema, categories, ranges, keys, ordering, temporal and clinical-plausibility checks. Error messages report table, column and count only, never cell values.
- **I/O and CLI**: canonical CSV or Parquet output plus `manifest.json` (config, versions, content hashes, environment); `datalife-fixtures generate` and `datalife-fixtures validate`.
- **Tests**: 41 tests covering determinism, cohort-size stability, config errors, forbidden fields, missingness, ordering, round trips, clinical plausibility, and a stale-fixture check.
- **Committed fixture**: 25 subjects under `tests/fixtures/`, regenerated by `scripts/regenerate_fixture.py`. Larger datasets go to the ignored `data/` folder.
- **CI**: adds a `python` job to the existing `CI` workflow (ruff, pytest, fresh generate + validate on Python 3.11 and 3.13; actions pinned by commit SHA on `ubuntu-24.04`). The existing `Scaffold quality` job is unchanged.
- `constraints.txt` pins verified dependency versions (numpy 2.4.4 on Python 3.11, where numpy 2.5 has no wheels; 2.5.3 on 3.12+).
- Small `.gitignore` fix: `data/` became `data/*` so the documented `data/README.md` can be tracked (the existing `!data/README.md` exception never applied).

## Reproduction and results

```bash
pip install -e ".[dev]" -c constraints.txt
pytest
datalife-fixtures generate --seed 42 --subjects 1000 --format parquet --out data/generated
datalife-fixtures validate data/generated
```

Expected: `41 passed`, then `{"subjects": 1000, "encounters": 5226, "observations": 15014}` and `ok`.

**Data version:** contract 0.1.0, generator 0.1.1.

**Cross-platform reproducibility:** seed 42 with 1,000 subjects gives identical canonical content hashes on:

| Environment | numpy | Result |
| --- | --- | --- |
| Windows, Python 3.12 | 2.5.3 | match |
| Linux, Python 3.13 | 2.5.3 | match |
| Linux, Python 3.11 | 2.4.4 | match |

Parquet bytes can vary with the pyarrow version, so equivalence is defined on the canonical CSV hashes recorded in the manifest.

**Data quality iteration:** a first audit found night-time visits, unpaired blood pressure and fasting glucose inconsistent with HbA1c. Fixed in generator 0.1.1 (separate commit) and now enforced by the validator and tests: clinic visits on weekdays 08:00-17:00 and urgent visits 07:00-23:00; SBP and DBP always paired with DBP below SBP; fasting glucose consistent with HbA1c (per-subject correlation about 0.8).

**Known limitations:**

- Distributions are generic and hand-set; synthetic realism is not clinical or external validity.
- Not-resulted missingness applies to lab markers only (GLU, HBA1C, HGB).
- No baseline or model in this PR; that is #3.

**Open questions for review:**

1. Should the contract file live inside the package (as now, so it ships with installs) or at a top-level `contracts/` folder?
2. Is the marker set (SBP, DBP, GLU, HBA1C, HGB, BMI) a reasonable minimum for v0.1.0, or should it wait for the #1 decision?
3. Is lab-only not-resulted missingness the right default?
