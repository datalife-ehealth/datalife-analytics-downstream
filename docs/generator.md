# Synthetic longitudinal fixture generator

Status: draft implementation for
[#2](https://github.com/datalife-ehealth/datalife-analytics-downstream/issues/2),
built against the draft v0.1.0 contract proposed in
[#1](https://github.com/datalife-ehealth/datalife-analytics-downstream/issues/1).
Field choices will follow whatever the #1 RFC accepts.

## What it produces

Three long-format tables that mirror concepts already present in
`datalife-datalake-core` (opaque `subject_key`, payload `kind`, timestamps):

| Table | Grain | Key fields |
| --- | --- | --- |
| `subjects` | one row per synthetic subject | `subject_key`, `sex`, `age_band`, `region`, `enrolled_on` |
| `encounters` | one row per care contact | `encounter_id`, `subject_key`, `encounter_at`, `encounter_type` |
| `observations` | one row per scheduled marker measurement | `observation_id`, `subject_key`, `encounter_id`, `observed_at`, `marker_code`, `value`, `unit`, `source_kind`, `missing_reason` |

The full data dictionary, allowed values, plausible ranges, missingness semantics,
temporal rules, and versioning policy are in
[`src/datalife_analytics/contracts/v0_1_0/data_dictionary.json`](../src/datalife_analytics/contracts/v0_1_0/data_dictionary.json).

## Privacy by construction

- No names, government identifiers, phone numbers, email addresses, addresses, or
  birth dates are generated. Age is a band; region is a synthetic code that maps to
  no real geography.
- `subject_key` is random bytes from the seeded generator, not a hash of anything.
- The validator rejects any column whose name matches the contract's
  `forbidden_field_patterns`, and its error messages never echo cell values.
- Distributions are rough, hand-set, and generic. They are not fitted to or sampled
  from any real dataset. Synthetic realism is not clinical or external validity.

## Missingness

- **Structural:** a marker not scheduled at an encounter has no row.
- **Not resulted:** a scheduled marker whose result never arrived has a row with a
  null `value` and `missing_reason = "not_resulted"`. The rate is configurable.

## Reproducibility

- Each subject draws from its own child of `numpy.random.SeedSequence(seed)`, so
  subject *i* is identical regardless of cohort size.
- Tables hold canonical text for dates and timestamps; CSV output is byte-for-byte
  reproducible from a fixed seed.
- Parquet bytes can vary with the `pyarrow` version. Canonical equivalence is
  defined as equal SHA-256 hashes of the canonical CSV form, which the manifest
  records for every table regardless of output format.
- NumPy guarantees stable bit streams but may change distribution algorithms across
  major versions; the manifest records library versions so a drift can be traced.

## Usage

```bash
datalife-fixtures generate --seed 42 --subjects 1000 --start 2024-01-01 --end 2025-12-31 \
  --format parquet --out data/generated
datalife-fixtures validate data/generated
```

From Python:

```python
from datalife_analytics.generator import GeneratorConfig, generate
from datalife_analytics.contract import validate

tables = generate(GeneratorConfig(seed=42, n_subjects=500))
validate(tables)
observations = tables["observations"]
```

## Committed fixture versus generated data

| Data | Location | In Git |
| --- | --- | --- |
| Small test fixture (25 subjects) | `tests/fixtures/synthetic_v0_1_0_*` | yes, regenerated by `scripts/regenerate_fixture.py` |
| Local datasets of any size | `data/` | never (ignored) |

`tests/test_fixture.py` fails if the committed fixture no longer matches what the
generator produces, so a generator change cannot silently alter test data.

## Extending without breaking a contract version

1. **New optional field or table, or new allowed value:** add it to a *new* contract
   folder (`contracts/v0_2_0/`), bump the minor version, and keep `v0_1_0` intact so
   existing consumers keep validating.
2. **Renamed, removed, or retyped field, or changed unit:** major version bump.
3. **New generator module** (for example medications or a new marker family): give it
   its own stream with `np.random.SeedSequence(seed, spawn_key=(...))` or a new
   child per subject, so values from existing modules do not shift.
4. Add tests for the new constraints, regenerate the fixture, and explain the change
   in the pull request.
